## Empirical results — §N answered on the server (2026-09-04)

Seven probes run against the real engine (`test/models/zz_handoff_probe_test.rb`,
`test/integration/zz_handoff_route_probe_test.rb`, both deleted after reading).
Nothing was implemented: the probes create the state §T item 3 says a handing-off
run sets, then ask the existing engine what it makes of it.

### The nested-handoff critical is real, and reproduces at the route level

| Probe | Result |
|---|---|
| 1 | A `awaiting_subflow`; `active_child_scenario` **nil** (a completed child is invisible to it); `parked?` **true**; `process_subflow_completion` returns true and sets **`A.status = "active"`**, advancing A onto its post-sub_flow step. **Resurrection reproduced.** |
| 2 | With `completed_at` 400 days old: A is **not** in `Scenario.terminal`, **not** in `stale_simulations`. **Permanent leak reproduced.** |
| 3 | Control: a *normally* completed child produces the identical `"active"`. A transferred child is **indistinguishable** from a finished one — which is why the resurrection happens. |
| 5 | Route level, C as a bare root (draft 3 as written): `GET /player/scenarios/:a/step` → **200, renders A, offers Resume.** The agent can resurrect A while C is live. |

Also confirmed incidentally: `update!` with `outcome: "transferred"` is **refused**
by the `OUTCOMES` inclusion validation, so §T item 3's enum extension is load-bearing,
not housekeeping.

### §N is decided: option (a), inherit `parent_scenario_id`

| Probe | Result |
|---|---|
| 6 | C inherits the handing-off run's `parent_scenario_id`: `GET` on A → **302 → C's step URL**, no Resume offered. **The hole closes with zero new code** — the existing `runner_step_redirect:66` already carries the agent forward. |
| 7 | Top-level handoff (A is a root, so C inherits nil and is a root): `GET` on A → **200, "This run is complete", no forward redirect.** |

**Conclusion, and it is now a finding rather than a recommendation:**

- **Take option (a).** It costs nothing and it closes the nested case for free.
  Option (b) — refusing handoffs inside sub_flow targets — is unnecessary.
- **§T item 14's `handed_off_to` forward branch is still required**, and probe 7
  is its regression test. Inheritance covers the nested case; only item 14 covers
  the top-level one. Neither substitutes for the other.
- Probe 4's first assertion was wrong and is worth recording: `parked?` is **true
  for a healthy in-progress sub-flow too**, because the agent is redirected away
  before it is ever consulted. `parked?` is not the predicate that tells you
  whether this works — the route is. Draft 3's §N reasoned from `parked?`.

## Empirical results — the Assignment, run 2026-09-04

A subagent with **no exposure to this design session** (it has never seen the word
"handoff") was given the app's real generated import prompt, the published JSON
Schema, and one realistic support domain: a billing-portal login diagnosis that
splits into four substantial procedures. It was asked to author the content the
way it genuinely thought it should be structured, and to report what the schema
would not let it express. Artifacts in the session scratchpad.

### Q1 — Does it decompose? **Yes. Five workflows.**

And not because of step count. Its stated reasons:

- **Reuse** — calls arrive pre-diagnosed ("IT told me my SSO is broken"). Those
  should enter at the procedure, and only a separate workflow can be entered
  directly, shared or embedded.
- **Ownership and publish cadence** — Collections owns the suspension script,
  Tier 2 Identity owns SSO. One workflow means every payment-wording edit touches
  the file Tier 1's SSO steps live in, gated by one `lock_version`.
- **Maintenance** — the monolith is ~70 steps, and the builder step list is flat.

Its own summary is the finding: *"The monolith… is frictionless **because** the
schema makes the correct structure expensive. That asymmetry is the finding, not
the step count."* **Premise 1 holds, and is now evidenced rather than predicted.**

### Q2 — Endings or mid-flow? **Endings. Approach A is validated; C is not needed.**

This was the decisive question, and it was asked without naming the options.
Unprompted, it wrote:

> *"**`sub_flow` cannot mean 'hand off and end.'** … **Wanted instead:** either
> `transitions` optional on `sub_flow` (terminal hand-off), or a way for the
> parent to branch on the child's resolution type."*

That is Approach A, arrived at independently. On the one case that looked mid-flow
(a question step whose help text tells the agent in prose to go start another
procedure) it said: *"If `sub_flow` could be terminal, I would have made it a
`sub_flow` without hesitating."* A mid-flow *source* is expressible under A as a
transition **into** a terminal handoff node — no cross-workflow edge required.

**One case neither A nor C covers, and it is new.** In the unlock procedure, a
step discovers the diagnosis mis-routed and wants to return to the router **at
`classify-cause`** — not at its start — with identity verification preserved.
Blocked twice: a `sub_flow` back would be a circular reference, and
`start_step_id` sets the entry point for the *whole workflow*. Its workaround is a
`resolution_type: "cancelled"` and prose telling the agent to redo the call by
hand. **Out of scope here; record it as a separate capability (re-entry at a
named step) rather than stretching this design to cover it.**

### Q3 — Does it expect `sub_flow` not to return? **Yes, and the workaround corrupts reporting.**

Five `sub_flow` steps. Because the schema forces `transitions` with `minItems: 1`
on `sub_flow`, it had to author a parent step whose only job is to exist: one
shared `procedure-complete` resolve with a single fixed
`resolution_type: "success"` covering four outcomes that include Account Security
holds and declined manager approvals. Its own words: **"the resolution reporting
on this workflow is a lie by construction,"** with `notes_required: true` as the
mitigation. This is what the feature's absence costs today.

### Premise 2, proven by the app's own validator

`StrictImportValidator` run as an admin with 13 published workflows visible:

| File | Errors | Warnings |
|---|---|---|
| 1 password-reset | 0 | 0 |
| 2 account-unlock | 0 | 0 |
| 3 sso-misconfiguration | **1** × `unknown_sub_flow_target` | 0 |
| 4 billing-suspension | 0 | 0 |
| 5 **login-diagnosis-router** | **4** × `unknown_sub_flow_target` | 0 |

**Zero structural errors anywhere.** An LLM produced correct content, and the only
thing wrong with it is that the cross-workflow references cannot resolve — the
router is invalid until someone clicks publish four times, in the right order.
That is Wave 1's justification, measured.

### Three findings unrelated to handoff, surfaced by the same test

1. **A `select` form field cannot declare its choices.** The form option object is
   `additionalProperties: false` with only `name, label, field_type, required,
   position`, while `field_type` accepts `"select"`. Verified directly against
   `public/schemas/turboflows-workflow-v1.json`. The generator's workaround was to
   list the choices inside the label text — which renders **a dropdown with no
   options**. This is a live authoring bug today, independent of this design.
2. **`variable_mapping` is undocumented**, so the generator refused to use it —
   "designing a cross-file variable contract on an undocumented merge rule is not
   something I'd hand to a live call floor." Consequence: its children re-ask for
   data the router already collected. Cheap fix (one prompt line plus a schema
   `description`), and it matters here — variable carryover is half of what this
   feature is for, and nobody will use it while it is unexplained.
3. **`can_resolve` is undocumented** in both prompt and schema, and went unused
   for the same reason.

## The finding that should change how you build this

Three review rounds. Three criticals, all of the same class, each found **only by
reading the code** — never by reasoning about the design. Twice the offending line
was literally `scenario.rb:314`.

That is not a document-quality problem. It is a fact about this subsystem: the
scenario traversal machinery has enough *implicit* coupling that an enumeration
of change sites cannot be trusted, however careful. The couplings that bit are
all of one shape — **a reader that infers run structure from `parent_scenario_id`
or `root_scenario` rather than being told it**:

| Reader | What it infers | How it broke |
|---|---|---|
| `auto_processable?:44` | "has a parent ⇒ its ending is internal" | ending swallowed |
| `descend:117` via `active_child_scenario` | "next frame is a child row" | run orphaned |
| `parked?:416` + `process_subflow_completion:270` | "awaiting + no active child ⇒ resume the newest completed one" | parent resurrected |
| `root_scenario` (4 call sites) | "the run starts at the top of the parent chain" | thread truncated, embed lost |

**Practical consequence: do not implement Wave 2 from this document alone.**

1. **Write the regression tests first**, from §Success Criteria — especially 4,
   4a, 4b and §N's *"A → sub-flow B → handoff C must not leave A resumable."*
   Each of the three criticals is a test that fails before any of them is a site
   in a list.
2. **Spike it on a branch before committing to the plan.** A two-day spike that
   runs one real handoff end-to-end will find the fourth coupling faster than a
   fourth review round would.
3. **Consider extracting the "where does this run live" question into one
   method** (`run_origin`, §T item 13a) rather than adding a fourth inference
   site. Four of the findings above collapse into that one primitive.

The import half (Wave 1) shows none of this — its claims verified exactly on the
first pass, because the strict-import path is explicit by design. **The risk is
entirely in Wave 2.**

## Problem Statement

A workflow can end, but it cannot point anywhere. When a diagnostic flow exhausts
itself and the agent now needs a different, more specific flow, the run simply
stops — `runner/_thread_complete.html.erb:11-14` offers a single exit, **View
results**; `player/show.html.erb:82-83` offers **Run Again** and **Back to
Workflows**. Either way the agent leaves the run, finds the next workflow by
name, and starts over, re-collecting every variable they already gathered with
the customer on the line.

Sub-Flow is not this. `ScenarioStepProcessor#process_subflow_step` is a
**call/return**: it creates a child `Scenario`, copies `results` in through
`variable_mapping`, parks the parent in `awaiting_subflow`, and resumes the
parent at `resume_node_uuid` when the child finishes. What is missing is the same
capability **without the return** — a tail call rather than a call.

## Demand Evidence

Honest accounting: **there is no runtime demand.** No agent has hit the dead end.
The driver is entirely generator-side.

The stated source is AI-generated workflows. An LLM handed
`public/schemas/turboflows-workflow-v1.json` and the `ImportPromptGenerator`
prompt will naturally decompose a large troubleshooting domain into several
linked workflows — and today it **cannot express that at all**.

The supporting evidence is that this friction already exists for a shipped
feature. `StrictImportValidator` carries this comment (`strict_import_validator.rb:158`):

> *"A draft match gets its own code. Imports land as drafts, so 'import A, then
> import B whose sub_flow targets A' fails where it used to work"*

The problem was encountered during the strict-import work and papered over with a
better error message (`sub_flow_target_not_published`) rather than solved.

## Status Quo

Two workarounds, both bad, neither yet measured:

1. **Author one large workflow** instead of several clean ones, to avoid creating
   a dead end. Costs authoring clarity and reuse.
2. **Import a linked set one file at a time, in dependency order.** Because
   `Workflow.visible_to` is published-only (`workflow.rb:106`) and every import
   lands as `draft`, a five-workflow set needs nine operations in a strict order
   the operator must derive themselves: import A → **publish A** → import B →
   **publish B** → import C…

   And the envelope forbids the bundle outright:
   `"workflows": { "minItems": 1, "maxItems": 1 }` (`import_schema_generator.rb:62-64`)
   — *"This version accepts exactly one workflow per file."*

## Target User & Narrowest Wedge

**User:** the workflow author (and the LLM acting on their behalf), not the
call-centre agent. The agent is the beneficiary; the author is the one blocked.

**Wedge:** a generated set of linked workflows imports as one file and runs as
one call. Everything else — richer conditions, handoff analytics, a builder
picker beyond a target dropdown — is later.

## Constraints

- **Rails 8.1, no Node.** Hotwire, importmap, Propshaft, vanilla CSS.
- **Self-hosted single install**, ~1300 internal users, SQLite/solid_* per the
  ONCE migration. No multi-tenancy.
- **A new step type is expensive.** Learning `form-step-type-surface-area`
  (10/10): the Form type was missing from **14 locations across 10 files**.
- **`StepFieldMap` is the single declaration of which fields exist**, read by five
  consumers. A field missing from `StepSerializer` is *erased from the workflow
  when someone restores a version*; `test/services/step_field_map_test.rb` is the
  guarantee.
- **Round-trippability is binding.** `ExportsController` emits
  `StepSerializer.call(@workflow, dialect: :strict)`; an exported file must remain
  a valid strict import file. **The first draft violated this** — see Wave 2 §R.
- **`SCHEMA_VERSION` is `"1"`.** Widening the envelope and adding an optional
  field are both backward-compatible; exempting a step type from the
  `transitions` requirement is a **loosening**, so old files still validate.

## Premises

All five were put to the user and agreed. One is amended by the review:

1. Demand is **generator-side**, not agent-side.
2. "Point forward" and "import a bundle" are **one problem**. `sub_flow` proves it.
3. Branching needs **no new routing logic** — a workflow's several endings already
   select which one is reached, so one target per ending yields conditional
   handoff for free.
   **Amended:** as originally worded ("one target per *ending*") this described
   Approach B. Under the chosen approach an ending is *either* a Resolve *or* a
   handoff step; the premise holds — the graph still picks which terminal you
   land on — but no Resolve carries a target.
4. A **new step type is the last resort**.
5. Shipping the pointer without the envelope ships **half a feature**.

## Approaches Considered

All approaches share the **bundle envelope work** (Wave 1); the choice concerns
only the handoff's shape.

### Approach A: Tail-call — `returns` flag on Sub-Flow — **CHOSEN**
`sub_flow_returns` boolean, default `true`. When `false`, the run transfers to the
target and does not come back.

- **Reuses:** `variable_mapping`, `SubflowValidator`'s cross-workflow reference
  walk, the target-resolution path in `StrictImportValidator`, and (with the
  traversal change in Wave 2 §T) the thread/results rendering.
- **Cost:** honest count is ~10 fork sites, not one — enumerated in Wave 2.

### Approach B: `continue_workflow_id` on Resolve
Puts the pointer on the ending card, matching the author's phrasing literally.

- **Rejected because:** it makes "every workflow must have ≥1 Resolve"
  satisfiable by Resolve steps that never resolve, so a workflow that can
  provably never end passes publish validation. A also has a
  never-ends failure mode (an A→B→A chain), but A's is caught by a validator that
  already exists and walks `sub_flow_workflow_id`; B's would need a new one.
  **This is a narrower discriminator than the first draft claimed** — see
  §Corrections.

### Approach C: Cross-workflow Transition (handoff as an edge)
Conceptually the truest model, and conditions come free via `ConditionEvaluator`.

- **Rejected because:** "transitions connect steps within the same workflow" is
  load-bearing for `GraphValidator`, `StepResolver`, `FlowDiagramService`, the
  transition editor and the schema's transition shape.
- **Settled 2026-09-04.** The Assignment was run: a cold generator asked for
  terminal handoff in its own words and never asked for a mid-flow edge. C is not
  needed. See §Empirical results — the Assignment.

### Approach D: Envelope only, defer the handoff
- **Rejected:** doesn't deliver the capability, and needs two shipping events.
  Note its claimed side benefit ("fixes `sub_flow`'s ordering pain") holds only
  *within* one bundle — see §Known Gaps.

## Recommended Approach

**Approach A, delivered in two waves — with the handed-to run modelled as a new
root scenario, not a child.**

### The structural decision that makes this tractable

The first draft kept `parent_scenario_id` set on the handed-to scenario. That one
fact breaks the feature in five places at once, and the failure is silent:

`ScenarioSettler.auto_processable?` (`scenario_settler.rb:44`) returns true for a
resolve step whenever `scenario.parent_scenario_id.present?` — so **the
handed-to workflow's ending is never shown to the agent**. `settle` then calls
`ascend` (`:129`), which calls `parent.process_subflow_completion`, which sets
`self.status = 'active'` unconditionally (`scenario.rb:314`) — **resurrecting the
run you just settled** — and with `resume_node_uuid` nil falls through to
`advance_to_step_uuid(nil)` and `check_completion`, overwriting the outcome. The
run ends resting on a re-completed *first* workflow with the second workflow's
ending invisible.

**Fix: the handed-to scenario is a root** (`parent_scenario_id: nil`) with a new
`handed_off_from_id` back-link, and an inverse `has_one :handed_off_to`.

The forks that read `parent_scenario_id` **negatively** then behave correctly for
a root with no change: `auto_processable?:44`, `ascend:129`,
`runner_step_redirect:60`, `parked?:416`, `stop!:183-185` (the transferred half
is `terminal?`, so `stop_frame!:198-199` returns early and cannot overwrite its
outcome), `runner_thread_current_depth` (`runner_helper.rb:29-34`, returns 0 for
a root).

**But the forks that read it _positively_ are where the new cost lands, and this
is not free.** `ScenarioSettler#descend` (`:117-122`) finds the next frame via
`current.active_child_scenario`, which is `child_scenarios.find_by(...)` —
i.e. the `parent_scenario_id` FK (`scenario.rb:145-147`). Set it to nil and
`descend` returns nil, the `settle` loop breaks, and **the handed-to run is
created in the database and never reached.** The `settle` loop
(`scenario_settler.rb:71-88`) branches on exactly two outcomes —
`awaiting_subflow?` and `resolved?` — and `ScenarioStepProcessor::Outcome`
(`:25-41`) has no status meaning "the run moved to a different root." Building
that forward path is Wave 2 §T item 12a and it is structural work.

**Why new-root anyway — on semantics, not site count.** Honest comparison:
special-casing the flag inside parent/child is ~5 guards
(`auto_processable?:44`, `ascend`, `runner_step_redirect:60`,
`flatten_path_entries` depth, `runner_thread_current_depth`); new-root is ~8
sites, several structural. New-root is still correct, because the alternative
leaves a parent parked in `awaiting_subflow` that will never return — a state
the data asserts and the run contradicts. Two records with two settled outcomes
is honest; a permanently-awaiting parent is a lie that every later reader of
`Scenario` has to learn about.

Separately, this fixes an over-claim in the first draft: `flatten_path_entries`
renders child entries at `depth + 1` behind a `group_start` mark, and a
non-returning child **never outdents**, so chaining three workflows would have
indented the transcript three levels.

**What this means for the run model:** the agent's experience is unchanged — one
continuous transcript, variables carried, no re-entry. The *records* are a chain
of two scenarios rather than one nested tree. That is a change from what was
agreed in session ("one run"), and it answers Open Q2 more cleanly: two
scenarios, two outcomes, one chain that reporting can follow.

### Wave 1 — the bundle envelope (human ~2 wks / CC ~6-8 hrs)

1. `ImportSchemaGenerator`: raise `maxItems` from 1; update the envelope
   description. Regenerate `public/schemas/turboflows-workflow-v1.json`.
2. `StrictImportValidator#extract_single_workflow` → validate many. The error
   paths hardcoding `workflows[0]` are, by `grep -n 'workflows\[0\]'`:
   **`:130, :145, :167, :225, :315, :326, :333, :360, :363, :460`**, plus two
   bare `"workflows"` paths at `:117` and `:122` that also need index-awareness.
   (The first draft listed seven and was wrong; this list is from the grep.)
   Each needs a fixture, per the existing "every documented error has a fixture"
   rule. This is the bulk of the diff.
3. **Intra-bundle reference resolution.** Today `resolve_sub_flow_targets`
   mutates in place — writes `step["target_workflow_id"]` and deletes
   `target_workflow_title` (`:170-172`). A workflow that does not exist yet has
   no id. **Decide the mechanism explicitly:** two-pass (index bundle titles →
   order topologically → create all workflows → resolve cross-refs in a second
   pass inside the same transaction) is the recommended shape. The rule "targets
   must be published" becomes **"published, or present in this bundle."**
4. **Reuse `SubflowValidator` rather than reimplementing cycle detection.** Order
   creation topologically, then run the existing
   `validate_no_circular_subflows` post-insert inside the transaction.
   Note `MAX_DEPTH = 10` measures **nesting**; a tail call has no stack, so a flat
   11-workflow chain must not be refused for a depth that no longer exists —
   handoff edges need their own limit or none.
5. **`WorkflowImporter::Result` carries a singular `:workflow`** (`:2`) and every
   reader assumes one: `imports_controller.rb:38`, `:44`, `:65`
   (`redirect_to workflow_path(result.workflow)` — undefined for N), `:89-95`
   (`import_summary`). Decide where a 5-workflow import redirects to.
6. `app/views/workflows/imports/report.html.erb` previews one workflow.
7. `WorkflowPlacement`: **per-workflow only.** Bundle-level placement with
   per-workflow override is a configuration surface nobody asked for.

### Wave 2 — the tail call (human ~2-3 wks / CC ~1 day)

Effort revised upward from the first draft's "~1 wk": the site list below is the
reason.

**Data**
1. Migration: `steps.sub_flow_returns` boolean, `default: true, null: false`
   (default true is what keeps every existing sub-flow unchanged); and
   `scenarios.handed_off_from_id` with an index and FK.
2. `StepFieldMap::BY_TYPE["sub_flow"] += [:sub_flow_returns]`; confirm
   `step_field_map_test.rb` covers it through publish/restore, export/import and
   a controller PATCH.
3. Extend `Scenario::OUTCOMES` (`:68`) with `"transferred"`. **The handing-off
   run sets, exactly:** `status: "completed"`, `outcome: "transferred"`,
   `current_node_uuid: nil`, `completed_at: Time.current` (via
   `record_completion`). `status` must be one of the enum's six (`:15-21`) and
   `"completed"` is the only member in `TERMINAL_STATUSES` (`:27`) that reads
   correctly here — it makes `terminal?` true (so `stop_frame!` won't overwrite
   the outcome), `parked?` false, and both cleanup scopes applicable.
   `"transferred"` lives on `outcome`, which is the column that distinguishes
   *how* a run ended.

**Graph / validation**
4. **`GraphHashBuilder#call` emits only `id`/`type`/`title`/`transitions`**
   (`graph_hash_builder.rb:27-38`). `GraphValidator` cannot see the new flag at
   all. Add it here first — consumed by `workflow.rb:414`,
   `workflow_health_check.rb:51` and `workflow_graph_converter.rb:143`.
   **Second site:** `workflow_graph_converter.rb:168-175` **hand-builds its own**
   `{"id","type","title","transitions"}` hash and never calls `GraphHashBuilder`,
   so it must be patched separately or its simulated graph stays blind to the
   flag and emits a spurious `terminal_not_resolve`.
5. `GraphValidator`: a non-returning `sub_flow` is a legal terminal for both
   `validate_terminals` and the `:no_path_to_resolve` reverse BFS.
6. `WorkflowHealthCheck:95-97` marks `terminal_not_resolve` as
   `fixable: true, fix_type: "add_resolve_after"`. Left alone, the health panel
   flags every handoff and offers a **Fix button that corrupts it**.
7. `StepResolver#terminal?` (`:59-64`) is explicitly
   `step.transitions.empty? && !step.is_a?(Steps::SubFlow)` — a transition-less
   SubFlow is deliberately *not* terminal. Must fork on the flag.
8. `Step#terminal?` (`step.rb:53`) is `transitions.empty?`, and
   `condition_summary` prints "Terminal" only for `Steps::Resolve`. A handoff
   renders as a non-terminal dead node in `_step_row.html.erb:53` and
   `_flow_diagram_panel.html.erb:44`.

**§R — Round-trip (fixes the constraint violation)**
9. `ImportSchemaGenerator:109` sets `properties["transitions"] = transitions_property
   unless type == "resolve"`, and `transitions_property` (`:213`) is
   `minItems: 1`. **The published schema forbids the exact shape this feature
   exists to let an LLM emit.** Exempt a non-returning sub_flow.
10. `StrictImportValidator#validate_step_transitions` (`:437-451`) raises
    `missing_transitions` for any non-resolve step with no transitions —
    so an exported workflow containing a terminal handoff is refused on
    re-import. Same exemption.
11. `ImportSchemaGenerator#property_for` (`:151-165`) types unknown fields as
    `{"type":"string"}`. Add `sub_flow_returns` to the boolean branch alongside
    `:can_resolve, :reason_required` or the published schema lies about it.

**§N — Nested handoff: the decision this document must make**

11a. **A handoff step can live in a workflow that is itself a sub-flow target,
    and nothing can prevent that** — `sub_flow_returns` is a flag on a step in an
    ordinary workflow, and any workflow can be a sub-flow target. Shape:
    A (root) → returning sub_flow → B (child) → B's terminal is a handoff → C.

    With C created as a bare root, B ends `completed/transferred` and **A is left
    in `awaiting_subflow` forever.** `A.active_child_scenario`
    (`scenario.rb:145-147`) filters `status: %w[active awaiting_subflow]`, so the
    completed B is invisible → nil → `A.parked?` (`:416`) is **true** → the agent
    is offered Resume → the POST reaches `process_subflow_completion`, whose
    fallback is `child_scenarios.where(status: 'completed').order(updated_at: :desc).first`
    (`:270`) → **picks the transferred B** → `self.status = 'active'` (`:314`) →
    **A resumes while C is still live.** Two runs, one call.

    Collateral in the same shape: `stop!` (`:180-187`) walks `root_scenario` +
    `unfinished_descendants`, so A and C become independently stoppable halves;
    and `cleanup_stale` scopes on `terminal` (`:72`), which `awaiting_subflow`
    never is — **A leaks permanently.**

    **Decide one, and write the regression test for it:**
    - **(a) C inherits the handing-off scenario's `parent_scenario_id`**
      (nil at top level ⇒ root exactly as designed; set ⇒ genuine frame
      replacement, so `ascend:129` returns to A when C ends and
      `auto_processable?:44` correctly auto-processes C's resolve because C
      really *is* a child). Self-consistent, and it is what "tail call" means.
      **Recommended.**
    - **(b) Publish refuses a handoff in any workflow reachable as a sub_flow
      target.** Simpler to reason about, but it makes a workflow's legality
      depend on who points at it, which no current rule does.

    `parent_scenario_id` turns the grandparent's GET from "200, renders A with a

    Option (b) is unnecessary. Regression assertion: *A → sub-flow B → handoff C

12b. **The handoff branch must persist `@scenario` itself.** `Scenario#process_step:251`

12a. **The handover path — the piece the previous draft omitted, and without
    which the feature silently does nothing.** `ScenarioSettler#settle`'s loop
    (`:71-88`) branches on exactly two outcomes, and `#descend` (`:117-122`)
    finds its next frame through `active_child_scenario` — the
    `parent_scenario_id` FK. A root is invisible to it, so the loop breaks, the
    `Settled` result names the *old* scenario, and the agent is shown
    `runner/_thread_complete`. Required:

      `handed_off`, carrying the destination;
    - `has_one :handed_off_to, class_name: "Scenario", foreign_key: :handed_off_from_id`
      on `Scenario`;
    - a **third branch in the `settle` loop** that swaps `current` to the new
      root and continues, so the handed-to run is settled onto its first
      answerable step in the same POST.

13. **Transcript: forward traversal, not backward.** The first draft specified
    this against the wrong signature — `flatten_path_entries(path, depth = 0)`
    (`scenarios_helper.rb:114`) takes an **array**, not a scenario, so it has no
    record to walk `handed_off_from_id` from. It also isn't needed:
    `child_scenarios_for` (`:170-177`) resolves children by
    `Scenario.where(id: ids)` — a plain id lookup with **no parent FK involved**
    — so forward traversal from the chain head works through existing plumbing
    as long as the entry carries `child_scenario_id`. The change is one branch:

    ```ruby
    if entry["handed_off"].present? && entry["child_scenario_id"].present?
      flat << entry.merge("kind" => "handoff", "depth" => depth)
      child = children[entry["child_scenario_id"]]
      flat.concat(flatten_path_entries(child.execution_path || [], depth)) if child
    ```

    Note `depth`, not `depth + 1` — that is what stops the indent accumulating.
    `child_scenarios_for:171` must also collect ids from `handed_off` entries,
    not only `subflow_started` ones. Then add `Scenario#handoff_chain_head`
    (walk `handed_off_from_id` up) and start **both** callers from it:
    `flattened_execution_path:65-67` (reads `scenario.execution_path`) and
    `runner_thread_entries:80-82` (reads `scenario.root_scenario.execution_path`).

13a. **The chain head is a fixed point, not a walk — and getting this wrong
    regresses a shipped feature.** "Walk `handed_off_from_id` up" is not enough:
    for a run currently inside an *ordinary returning sub-flow* (child D of root
    A, no handoff anywhere), `handed_off_from_id` is nil, so a naive chain head
    returns D and `runner_thread_entries` reads **D's own path instead of A's** —
    silently truncating the thread to the sub-flow's steps. That is exactly what
    the comment at `scenarios_helper.rb:78-81` exists to prevent, and it renders
    on every step. `root_scenario` is not "the break"; it is *half* the walk.
    Alternate both links to a fixed point:

    ```ruby
    def run_origin
      frame = self
      loop do
        frame = frame.root_scenario
        break frame unless frame.handed_off_from
        frame = frame.handed_off_from
      end
    end
    ```

    Neither link alone is correct for a mixed chain A → sub-flow B → handoff C →
    sub-flow D.

13b. **One primitive, four call sites.** `run_origin` also answers three things
    this document previously treated as separate or missed entirely:
    - `player_controller.rb:55` — `@scenario.root_workflow.embeddable?`.
      `WorkflowSharing#embeddable?` is `shared? && embed_enabled?`
      (`workflow_sharing.rb:18`) and a handed-to workflow **has no share token**,
      so an embedded share-link run would lose embed mode at the boundary. This
      is the same bug the comment at `player_controller.rb:50-54` was written to
      fix for sub-flows, reintroduced. **Previously unlisted.**
    - `runner_shell.rb:82` and `:165` (`@workflow = scenario.root_workflow`) —
      this is also the answer to Open Q2's title-flip question.
    - `runner_shell.rb:133`, which makes item 15 fall out for free.

13c. `drop_child_terminal?` (`scenarios_helper.rb:142-168`) is deliberately **not**
    called on a handoff: a handed-to run's terminal Resolve is a real ending the
    agent was shown (criterion 4), unlike a returning child's. Stated so nobody
    "fixes" the omission later.

13d. **Cost the recursion carries.** `child_scenarios_for` issues one query per
    recursion level. Under sub-flows that was bounded by `MAX_DEPTH = 10`; an
    N-long handoff chain is N levels ⇒ **N queries per render, on every step**,
    plus an unbounded thread. Open Q4's chain cap is the mitigation. Termination
    itself is safe — `child_scenario_id` ids strictly increase, so the record
    graph is a DAG.

14. `RunnerShell#runner_step_redirect` needs a **new forward branch.** The
    branch that *won't* fire is `:60`
    (`complete? && parent_scenario`) — with `parent_scenario_id: nil` a finished
    handoff run is not sent backward into the settled parent. But a GET on the
    *handing-off* scenario after the handoff (refresh, browser Back, a bookmark)
    falls through every branch and renders `_thread_complete` with a
    `results_url` for the abandoned half. **Two traps in the obvious fix:**
    - `active?` is one enum member and `awaiting_subflow` is a **different** one
      (`scenario.rb:14-21`), so C sitting inside a sub-flow would get no
      redirect. Test `!terminal?` (`:191`).
    - `handed_off_to` is one hop. For A→B→C with B transferred and C live,
      `A.handed_off_to` is B and `B.terminal?` is true ⇒ no redirect — and
      Success Criterion 1 is explicitly *"3+ linked workflows."* **Walk
      `handed_off_to` to the chain tail**, then redirect if the tail is
      `!terminal?`.

15. `RunnerShell#respond_to_settled` (`runner_shell.rb:194`) computes
    `@thread_tail = helpers.runner_thread_entries(@scenario).drop(thread_before)`
    where `thread_before` was measured on the **pre-handoff** scenario (`:133`).
    Once `@scenario` is a new root, the entry count restarts and `.drop(n)`
    yields `[]` — the agent answers and nothing streams in. Measure against the
    chain head from item 13. (`next_url` is fine: `advance.turbo_stream.erb:12`
    uses `next_step_scenario_path(@scenario)` and follows the swap.)

16. `Scenario.cleanup_stale` (`:88-100`) reaps by each record's **own**
    `completed_at` and `purpose`; under parent/child, `:95`
    (`where(parent_scenario_id: batch_ids).delete_all`) took children with the
    parent. A chain is not a tree, so the transferred first half becomes an
    independent terminal record: if the handed-to run is still `active` (an
    agent left the tab open), the first half is reaped at 7/90 days and the
    surviving run **silently loses the first two-thirds of its transcript** —
    and with an `on_delete: :nullify` FK the back-link nulls, leaving no
    evidence. The requirement is not "must still reap it" but **must reap the
    chain atomically and must never half-reap it.**

    **Mechanism, since a requirement is not a plan:** exclude from both stale
    scopes (`:74-82`) any record whose chain tail is non-terminal, and reap from
    the tail so the whole chain ages on one clock. Pin the new FK's `on_delete`
    in item 1 — the draft assumed `:nullify` without saying so, and `:nullify` is
    what makes a half-reap leave no evidence.

17. **The views dispatch on `kind` and know only two values.**

## Open Questions

1. **Back navigation across a handoff — likely already answered.**
   `ScenarioNavigator#can_go_back?` (`scenario_navigator.rb:29-32`) reads only
   `@scenario.execution_path`; it does **not** walk the parent chain (`Scenario#stop!`
   at `:180-187` does). A freshly handed-to run has an empty `execution_path`, so
   Back is already impossible across the boundary. **Decide whether to leave it
   that way** (recommended — the previous run is settled, and reopening it means
   un-settling a recorded outcome) or to build cross-boundary Back deliberately.
2. **Reporting over a chain — `/admin/analytics`, not `/admin/data_health`.**
   `analytics_controller.rb:11` computes
   `@completed_count = @base_scope.where(outcome: %w[completed resolved escalated])`
   and `:18` groups by `outcome`; two further aggregates use raw SQL
   `outcome IN (...)` at `:126` and `:143`. `"transferred"` is in neither the completed nor
   the escalated bucket, so **completion rate silently drops for every handoff.**
   Decide whether a transferred run counts as completed (it did its job), or
   whether only the chain's last run counts. Related: `@workflow =
   @scenario.root_workflow` (`runner_shell.rb:82,165`) now returns the
   *handed-to* workflow, so the page title changes mid-run — arguably right, but
   it contradicts the comment at `:79-81` written to prevent exactly that, so
   make it a decision rather than a side effect.
3. **Does `SCHEMA_VERSION` bump to `"2"`?** Every change here is additive or a
   loosening, so `"1"` can likely stand. Confirm against `check_schema_version`.
4. **Handoff chain length limit — decide, don't defer.**
   `SubflowValidator::MAX_DEPTH = 10` measures nesting and does not apply.
   `Scenario::MAX_ITERATIONS` does not help either: `count_iteration!`
   (`scenario.rb:484-495`) resets per scenario, so a handoff cycle that slipped
   past publish validation would loop forever **inside one POST**, creating
   scenarios. Two things needed: a publish-time chain cap, and an iteration
   bound on the `settle` loop itself. Also give §T item 12a's third branch an
   `or break` for symmetry with `descend:76` — without it a nil destination
   exits the loop with `handed_off` still set, and `Settled` delegates only
   `blocked?/resolved?/halted?` (`scenario_settler.rb:23-25`), so
   `respond_to_settled` falls to the success path and renders the old run's
   completed card. Silent.

## Success Criteria

1. An LLM given `public/schemas/turboflows-workflow-v1.json` emits **one file**
   containing 3+ linked workflows, and it imports in **one** operation with no
   manual publish-ordering.
2. A run crossing a handoff shows **one continuous transcript, without increasing
   indentation** at each boundary. (Not free — Wave 2 §T item 13.)
3. Variables gathered before the handoff are readable after it. This one *is*
   nearly free: the target inherits the full `results` hash
   (`scenario_step_processor.rb:294`).
4. **The handed-to workflow's ending is shown to the agent** and is not
   auto-processed away. This is the regression test for the
   `auto_processable?` / `ascend` / `status = 'active'` failure above.
4a. **Answering the handoff step lands the agent on the next workflow's first
   answerable step, in the same POST** — not on a "This run is complete" card.
   This is the regression test for the draft-2 failure (§T item 12a): both
   drafts produced a feature that validated and did nothing, so this assertion
   is the one that proves the run actually moves.
4b. **A GET on the handed-off-from scenario after a handoff** (refresh, browser
   Back, bookmark) redirects forward to the live run, not to the abandoned
   half's results.
5. A handoff cycle (A→B→A) is refused at publish, with the cycle named.
6. **Export → re-import round-trips** a workflow containing a terminal handoff.
7. Every existing sub-flow keeps returning; no existing workflow changes
   behaviour.
8. The health panel does **not** offer `add_resolve_after` on a handoff step.
9. `step_field_map_test.rb` passes with the new field, including version restore.
